TeoriaA · Rodzaje relacji

Powiązanie dwóch tabel to klucz obcy: kolumna, która przechowuje id wiersza z innej tabeli. W JPA klucz obcy to pole typu encji, a nie Long.

Relacja Przykład W JPA Gdzie jest klucz obcy
wiele-do-jednego wiele rezerwacji → jeden stolik @ManyToOne + @JoinColumn w encji podrzędnej po stronie „wiele”: reservation.table_id
jeden-do-wielu stolik → jego rezerwacje @OneToMany(mappedBy = "table") + lista w encji nadrzędnej nigdzie nowego: to drugi koniec tej samej relacji
jeden-do-jednego gość ↔ jego konto użytkownika @OneToOne + @JoinColumn w tabeli, która wskazuje: guest.user_account_id (kolumna unikalna)
wiele-do-wielu rezerwacja ↔ dodatki (tort, kwiaty) encja łącząca z dwiema @ManyToOne albo @ManyToMany + @JoinTable w trzeciej tabeli, łączącej: reservation_extra.reservation_id i extra_id

Rezerwacja wskazuje na gościa i na stolik (dwie relacje wiele-do-jednego):

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "guest_id", nullable = false)
private Guest guest;

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "table_id", nullable = false)
private CafeTable table;

Stolik ma stronę odwrotną tej relacji. Wartość mappedBy to nazwa pola @ManyToOne w rezerwacji. Bez mappedBy Hibernate utworzyłby dodatkową tabelę łączącą, której nikt nie planował:

@OneToMany(mappedBy = "table")
private List<Reservation> reservations = new ArrayList<>();

Gość ma najwyżej jedno konto, a konto należy do jednego gościa. Relacja jest opcjonalna (gość bez konta), dlatego nie ma optional = false ani nullable = false:

@OneToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_account_id")
private UserAccount account;

Dane startowe. W kolumnie klucza obcego wpisujecie numer wiersza tabeli nadrzędnej (baza numeruje wiersze od 1 w kolejności poleceń insert). Sekcja tabeli nadrzędnej musi być wyżej niż sekcja tabeli podrzędnej:

-- ===== LAB 02 · guest =====
-- user_account_id: numer konta z sekcji user_account (1 = Ola, 2 = Kuba)
insert into guest (full_name, phone, user_account_id) values
    ('Anna Kowalska',  '600100200', 1),
    ('Jan Nowak',      null,        2),
    ('Ewa Wiśniewska', '600500600', null);

-- ===== LAB 03 · reservation =====
-- guest_id i table_id wskazują wiersze z sekcji powyżej
insert into reservation
    (guest_id, table_id, starts_at, party_size, status, deposit) values
    (1, 1, '2026-11-14 18:00:00', 2, 'NEW',       20.00),
    (1, 2, '2026-11-15 12:00:00', 4, 'CONFIRMED', 40.00),
    (2, 2, '2026-11-16 19:00:00', 3, 'NEW',        0.00);

Jak powstaje relacja wiele-do-wielu

Rezerwacja może mieć wiele dodatków (tort, kwiaty), a ten sam dodatek trafia do wielu rezerwacji. Kolumna klucza obcego mieści tylko jeden numer, więc nie da się jej wstawić ani do rezerwacji, ani do dodatku. Dlatego powstaje trzecia tabela, łącząca. Każdy jej wiersz to jedna para: numer rezerwacji i numer dodatku.

reservation            reservation_extra                extra
id | starts_at         reservation_id | extra_id        id | name
 1 | 14.11 18:00                    1 |        1         1 | Tort
 2 | 15.11 12:00                    1 |        2         2 | Kwiaty
                                    2 |        1

rezerwacja 1 ma tort i kwiaty, rezerwacja 2 ma tort
tort jest w dwóch rezerwacjach

Tabelę łączącą można zapisać w JPA na dwa sposoby. Dla danej pary tabel wybieracie jeden:

Sposób 1: encja łącząca Sposób 2: @ManyToMany
Kiedy para ma własne dane, np. ilość, uwagi, cenę w chwili zakupu para nie ma żadnych własnych danych: liczy się tylko to, że jest
Co piszecie nową klasę encji dla tabeli łączącej jedno pole w jednej z dwóch istniejących encji; nowej klasy nie ma
Kolumny tabeli łączącej id, dwa klucze obce i kolumny własne tylko dwa klucze obce

W bazie oba sposoby dają tę samą tabelę reservation_extra z dwoma kluczami obcymi; różni się tylko zapis w Javie. Relacja wiele-do-wielu to zawsze dwie relacje wiele-do-jednego spotykające się w tabeli łączącej: wiele wierszy tej tabeli wskazuje jedną rezerwację i wiele wskazuje jeden dodatek. W sposobie 1 piszecie tabelę łączącą sami jako encję, więc jej dwa klucze obce widać jako dwa pola @ManyToOne. W sposobie 2 tabelę łączącą tworzy Hibernate, a w kodzie zostaje jedno pole @ManyToMany, które ją opisuje.

Sposób 1: encja łącząca

  1. Tworzycie nową klasę encji nazwaną od pary, np. ReservationExtra z tabelą reservation_extra, w pakiecie entity modułu.
  2. Dopisujecie w niej dwa pola @ManyToOne, po jednym do każdej z łączonych tabel. Każde tworzy jedną kolumnę klucza obcego. Oba są wymagane (nullable = false), bo para bez jednej ze stron nie ma sensu.
  3. Dopisujecie kolumny własne pary, np. ilość i uwagi.
  4. W encjach Reservation i Extra niczego nie zmieniacie.
@Entity
@Table(name = "reservation_extra")   // tabela łącząca
public class ReservationExtra {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // której rezerwacji dotyczy ten wiersz
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "reservation_id", nullable = false)
    private Reservation reservation;

    // który dodatek został wybrany
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "extra_id", nullable = false)
    private Extra extra;

    // dane własne pary: ile sztuk
    @Column(name = "quantity", nullable = false)
    private Integer quantity;

    // dane własne pary: uwagi
    @Column(name = "note", length = 120)
    private String note;

    protected ReservationExtra() {
    }
}

Encja łącząca jest zwykłą tabelą: obowiązują ją reguły LAB 02 (co najmniej 4 kolumny poza id, tutaj dwa klucze obce i dwie kolumny własne, oraz co najmniej 3 wiersze danych). Dane wpisujecie pod sekcjami obu łączonych tabel:

-- ===== LAB 03 · reservation_extra =====
insert into reservation_extra (reservation_id, extra_id, quantity, note) values
    (1, 1, 1, null),            -- rezerwacja 1: tort, 1 sztuka
    (1, 2, 2, 'róże'),          -- rezerwacja 1: kwiaty, 2 sztuki
    (2, 1, 1, null);            -- rezerwacja 2: tort, 1 sztuka

Sposób 2: @ManyToMany

  1. Nie tworzycie nowej klasy. Wybieracie jedną z dwóch encji, zwykle tę, od której czytacie relację („rezerwacja ma dodatki”), tutaj Reservation.
  2. Dopisujecie w niej jedno pole: zbiór obiektów drugiej encji.
  3. W drugiej encji (Extra) niczego nie dopisujecie.
  4. Tabelę łączącą Hibernate tworzy sam, według opisu w @JoinTable.
// w klasie Reservation, obok pozostałych pól
@ManyToMany
@JoinTable(name = "reservation_extra",
        joinColumns = @JoinColumn(name = "reservation_id"),
        inverseJoinColumns = @JoinColumn(name = "extra_id"))
private Set<Extra> extras = new HashSet<>();
Element Znaczenie
@ManyToMany rezerwacja ma wiele dodatków, a dodatek może należeć do wielu rezerwacji
@JoinTable(name = "reservation_extra") nazwa tabeli łączącej, którą Hibernate utworzy w bazie. Tej tabeli nie odpowiada żadna klasa
joinColumns = @JoinColumn(name = "reservation_id") kolumna tabeli łączącej, która wskazuje na tę encję, czyli tę, w której piszecie pole (Reservation)
inverseJoinColumns = @JoinColumn(name = "extra_id") kolumna tabeli łączącej, która wskazuje na drugą encję, czyli typ w nawiasach ostrych (Extra)
Set<Extra> extras = new HashSet<>() w Javie rezerwacja trzyma zbiór swoich dodatków. Set, a nie List, bo ta sama para nie może wystąpić dwa razy

Po uruchomieniu aplikacji w logu jest tabela, której nie ma w kodzie jako klasy:

create table reservation_extra (
    extra_id bigint not null,
    reservation_id bigint not null,
    primary key (extra_id, reservation_id)
)

Dane tej tabeli to same pary numerów wierszy, wpisane pod sekcjami obu łączonych tabel:

-- ===== LAB 03 · reservation_extra =====
insert into reservation_extra (reservation_id, extra_id) values
    (1, 1),                     -- rezerwacja 1: tort
    (1, 2),                     -- rezerwacja 1: kwiaty
    (2, 1);                     -- rezerwacja 2: tort

ZadanieC · Relacje w kodzie

Na ocenę 3 wystarcza C1 z jedną relacją i dane z części D. Na ocenę 4 potrzebne są wszystkie trzy rodzaje relacji: C1 (dwie relacje), C2 i C3.

C1. Wiele-do-jednego: jedna relacja na ocenę 3 (R3.01), dwie na ocenę 4 (R3.03)

W encji podrzędnej (strona „wiele”) dopiszcie pole typu encji nadrzędnej:

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "<tabela_nadrzędna>_id", nullable = false)
private <EncjaNadrzędna> <pole>;

Relacja opcjonalna nie ma optional = false ani nullable = false. Pole dodajcie do konstruktora i wygenerujcie getter.

C2. Jeden-do-wielu: co najmniej jedna relacja, ocena 4 (R3.04)

W encji nadrzędnej dopiszcie listę wierszy podrzędnych. Są dwa poprawne zapisy.

Relacja dwukierunkowa (zalecana): encja podrzędna ma już pole @ManyToOne z C1, a lista jest drugim końcem tej samej relacji. mappedBy to nazwa tego pola. Lista nie tworzy kolumny i nie wymaga danych w data.sql:

// w encji nadrzędnej, np. CafeTable
// w Reservation jest pole: private CafeTable table
@OneToMany(mappedBy = "<pole @ManyToOne w encji podrzędnej>")
private List<<EncjaPodrzędna>> <pole> = new ArrayList<>();

Relacja jednokierunkowa: encja podrzędna nie ma pola @ManyToOne i nie wie o nadrzędnej, np. zamówienie zna swoje pozycje, a pozycja nie ma pola „zamówienie”. Wtedy zamiast mappedBy podajecie przy liście nazwę kolumny klucza obcego. Kolumna powstaje w tabeli podrzędnej, więc w data.sql wpisujecie ją w insert tabeli podrzędnej:

// w encji nadrzędnej, np. Order; klasa OrderLine nie ma pola typu Order
@OneToMany
// kolumna klucza obcego, np. order_id w tabeli order_line
@JoinColumn(name = "<tabela_nadrzędna>_id")
private List<<EncjaPodrzędna>> <pole> = new ArrayList<>();

@OneToMany bez mappedBy i bez @JoinColumn jest błędem: Hibernate tworzy wtedy dodatkową tabelę łączącą, której nie planowaliście.

C3. Jeden-do-jednego: co najmniej jedna relacja, ocena 4 (R3.05)

Wybierzcie parę obiektów, które występują jeden do jednego (osoba i konto, zamówienie i faktura, pojazd i dowód rejestracyjny):

@OneToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "<tabela_nadrzędna>_id")
private <EncjaNadrzędna> <pole>;

Po każdej relacji: klucze obce w data.sql (część D), Rerun, w logu alter table … add constraint … foreign key, potem Commit i Push.

ZadanieD · Dane powiązane (ocena 3)
  • Do polecenia insert tabeli podrzędnej dopiszcie kolumnę klucza obcego z numerem wiersza tabeli nadrzędnej (wzór w części A).
  • Sekcja tabeli nadrzędnej jest wyżej niż sekcja podrzędnej. Dane nowych tabel trafiają do sekcji -- ===== LAB 03 · <tabela> =====.
  • Każda relacja @ManyToOne i @OneToOne ma co najmniej jeden wiersz z wypełnionym kluczem obcym (R3.02).
  • W relacji @OneToOne dwa wiersze nie mogą wskazywać tego samego wiersza nadrzędnego.
  • Dane wpisujecie zwykłymi poleceniami insert z numerami wierszy. Zapytań z join ani podzapytań nie trzeba pisać.
  • Sprawdzenie w konsoli H2 (http://localhost:8080/h2-console, JDBC URL jdbc:h2:file:./data/wdtb, użytkownik sa): select * from <tabela_podrzędna> pokazuje wypełnione kolumny kluczy obcych.

Typowe błędy przy starcie

Komunikat w logu Przyczyna
Referential integrity constraint violation klucz obcy wskazuje wiersz, którego jeszcze nie ma: sekcja podrzędna nad nadrzędną albo za duży numer wiersza
NULL not allowed for column "…_ID" kolumna klucza obcego z nullable = false pominięta w insert
Column "…_ID" not found nazwa kolumny w insert różni się od @JoinColumn(name)
Unique index or primary key violation dwa wiersze wskazują ten sam wiersz w relacji @OneToOne
Unknown mappedBy in: … mappedBy nie jest nazwą pola @ManyToOne w encji podrzędnej

Błąd w data.sql zatrzymuje start aplikacji. Czytajcie log od pierwszej linii z Caused by: tam jest nazwa tabeli i kolumny.

ZadanieF · LAZY i repozytorium (ocena 5)
  • LAZY (R3.11). Każde @ManyToOne i @OneToOne ma fetch = FetchType.LAZY: wiersz nadrzędny jest pobierany dopiero wtedy, gdy kod o niego zapyta.
  • Repozytorium (R3.12). Interfejs w pakiecie pl.wsb.<projekt>.<moduł>.repository z zapytaniem, którego nazwa prowadzi przez relację: 
    public interface <Encja>Repository extends JpaRepository<<Encja>, Long> {

    List<<Encja>> findBy<PoleRelacji>_<PoleEncjiNadrzędnej>(<typ> wartość);
}
    Przykład nazwy: findByGuest_FullName(String fullName). Spring Data sprawdza nazwę przy starcie aplikacji (No property … found oznacza literówkę).
